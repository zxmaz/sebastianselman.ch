Azure Databricks and Azure AI Foundry Integration announced at Build 2025

Originally published on LinkedIn

At Microsoft Build 2025, a new integration between Azure Databricks and Azure AI Foundry was announced. Azure Databricks is a unified analytics platform optimised for Microsoft Azure (providing scalable data processing via Apache Spark), while Azure AI Foundry is a platform for developers to design and manage AI applications and agents. The integration (currently in preview) enables AI agents built in Azure AI Foundry to directly leverage enterprise data stored in Azure Databricks in real time[[1]](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Fnews%2Emicrosoft%2Ecom%2Fbuild-2025-book-of-news%2F&urlhash=2xHF&trk=article-ssr-frontend-pulse_little-text-block). It allows agents to execute live Spark jobs on Databricks and use Databricks’ AI/BI Genie (a natural language query interface for data) to retrieve insights[[1]](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Fnews%2Emicrosoft%2Ecom%2Fbuild-2025-book-of-news%2F&urlhash=2xHF&trk=article-ssr-frontend-pulse_little-text-block). Crucially, all data access remains governed by Azure Databricks Unity Catalog for security and compliance[[1]](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Fnews%2Emicrosoft%2Ecom%2Fbuild-2025-book-of-news%2F&urlhash=2xHF&trk=article-ssr-frontend-pulse_little-text-block). Below, I am aiming to address the significance of this change, who benefits from it, some imagined use cases, and its limitations.

So What? Why Is This Integration Relevant?

Bridging AI Agents with Enterprise Data: This integration addresses a core challenge in enterprise AI development: connecting AI agents with live business data in a secure, governed way. Many organisations want AI-powered assistants that can provide up-to-date, context-rich answers, but previously, those agents might have been limited to static knowledge bases or required complex custom integrations. The question at the core here is: “How can we enable AI agents to reason over our latest enterprise data and produce relevant answers, without compromising on governance or requiring manual data pipelines?” The Azure AI Foundry + Databricks integration is another Microsoft answer to that question (a similar integration from Foundry to Fabric was announced end of March [[8]](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Fblog%2Efabric%2Emicrosoft%2Ecom%2Fen-us%2Fblog%2Fempowering-agentic-ai-by-integrating-fabric-with-azure-ai-foundry%2F&urlhash=bKT7&trk=article-ssr-frontend-pulse_little-text-block)).

By natively connecting AI Foundry agents to Azure Databricks, agents gain real-time access to operational and analytical data stored in the Databricks lakehouse[[1]](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Fnews%2Emicrosoft%2Ecom%2Fbuild-2025-book-of-news%2F&urlhash=2xHF&trk=article-ssr-frontend-pulse_little-text-block). This means an agent’s responses can be grounded in the most current data (for example, yesterday’s sales figures or the latest sensor readings) rather than outdated snapshots. According to Microsoft’s announcement, this dramatically improves the quality and usefulness of AI agents by giving them domain-specific context[[2]](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Fwww%2Edatabricks%2Ecom%2Fblog%2Fannouncing-azure-databricks-native-connector-azure-ai-foundry&urlhash=x2z9&trk=article-ssr-frontend-pulse_little-text-block)[[4]](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Fazure%2Emicrosoft%2Ecom%2Fen-us%2Fblog%2Fpowering-the-next-ai-frontier-with-microsoft-fabric-and-the-azure-data-portfolio%2F&urlhash=d51-&trk=article-ssr-frontend-pulse_little-text-block). In other words, the agent isn’t merely a large language model in isolation; it becomes a data-aware assistant that can answer questions with actual business facts and numbers.

Data Intelligence for Better Answers: At Build, Microsoft emphasized that high-quality, production-ready AI agents require “data intelligence” – essentially, awareness of enterprise data and context[[2]](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Fwww%2Edatabricks%2Ecom%2Fblog%2Fannouncing-azure-databricks-native-connector-azure-ai-foundry&urlhash=x2z9&trk=article-ssr-frontend-pulse_little-text-block). This integration tackles that need. For instance, Azure Databricks’ AI/BI Genie is a feature that allows users to query data conversationally in natural language, returning answers that are specific to the business’s datasets[[2]](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Fwww%2Edatabricks%2Ecom%2Fblog%2Fannouncing-azure-databricks-native-connector-azure-ai-foundry&urlhash=x2z9&trk=article-ssr-frontend-pulse_little-text-block). By hooking Genie into Azure AI Foundry, an agent can now directly respond to a user’s question by running a live query on Databricks via Genie, rather than relying purely on pre-trained knowledge. The result is more accurate, context-rich answers to business questions, with the speed of natural language interaction[[2]](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Fwww%2Edatabricks%2Ecom%2Fblog%2Fannouncing-azure-databricks-native-connector-azure-ai-foundry&urlhash=x2z9&trk=article-ssr-frontend-pulse_little-text-block). This is highly relevant for organisations seeking to democratise data access – enabling non-technical users to get insights without writing SQL or waiting for a data analyst.

Unified and Governed Solution: Another reason this change is important is the emphasis on security, governance, and responsible AI. Enterprise data is often sensitive. The integration maintains strict access control through Databricks Unity Catalog, meaning any data the AI agent accesses must adhere to the same permission policies and auditing as regular Databricks workloads[[1]](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Fnews%2Emicrosoft%2Ecom%2Fbuild-2025-book-of-news%2F&urlhash=2xHF&trk=article-ssr-frontend-pulse_little-text-block). This addresses the common question of “How do we let an AI use our data safely?”. Furthermore, Azure AI Foundry brings Responsible AI and content safety features out-of-the-box[[1]](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Fnews%2Emicrosoft%2Ecom%2Fbuild-2025-book-of-news%2F&urlhash=2xHF&trk=article-ssr-frontend-pulse_little-text-block), which helps filter or mitigate problematic model outputs. By combining these, Microsoft is basically saying: “We’ve made it easier to build an AI agent that can use your real enterprise data — and we’ve made it safe and compliant to do so.” This relevant change opens the door for more trustworthy AI deployments in business settings, where previously there was hesitation to let AI loose on live data.

In summary, the integration is relevant because it unlocks real-time, data-driven intelligence for AI agents without requiring bespoke development. It answers the need for AI agents that are both smart and reliable – capable of conversing naturally while backed by up-to-the-minute data and robust governance[[2]](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Fwww%2Edatabricks%2Ecom%2Fblog%2Fannouncing-azure-databricks-native-connector-azure-ai-foundry&urlhash=x2z9&trk=article-ssr-frontend-pulse_little-text-block)[[4]](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Fazure%2Emicrosoft%2Ecom%2Fen-us%2Fblog%2Fpowering-the-next-ai-frontier-with-microsoft-fabric-and-the-azure-data-portfolio%2F&urlhash=d51-&trk=article-ssr-frontend-pulse_little-text-block). This significantly expands what enterprise AI assistants can do, moving from toy demos to truly useful business tools.

Who Benefits? Typical Enterprise Profiles

This new capability can benefit several types of users and roles in an enterprise:

  • AI Developers & Solution Architects: Developers building AI solutions are primary beneficiaries. Azure AI Foundry is aimed at developers (and IT admins) to design and manage AI agents[[3]](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Ftechcommunity%2Emicrosoft%2Ecom%2Fblog%2Fanalyticsonazure%2Fannouncing-the-availability-of-azure-databricks-connector-in-azure-ai-foundry%2F4414889&urlhash=PTYZ&trk=article-ssr-frontend-pulse_little-text-block). With this integration, developers can much more easily incorporate company data into their agents. They no longer need to develop custom connectors or ETL processes to feed data to the AI – it’s available natively. This speeds up development of intelligent applications and lets developers focus on the agent’s logic and user experience rather than data plumbing. Solution architects also benefit by being able to architect end-to-end AI systems on Azure with components that plug in seamlessly (Foundry, Databricks, etc.). Essentially, technical teams get a streamlined way to build powerful, data-aware AI apps[[3]](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Ftechcommunity%2Emicrosoft%2Ecom%2Fblog%2Fanalyticsonazure%2Fannouncing-the-availability-of-azure-databricks-connector-in-azure-ai-foundry%2F4414889&urlhash=PTYZ&trk=article-ssr-frontend-pulse_little-text-block).
  • Data Scientists & Analysts: Data professionals who use Azure Databricks (data engineers, data scientists) will see their work reach a wider audience. For example, the integration enables agents to leverage data scientists’ existing Spark jobs in Databricks[[1]](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Fnews%2Emicrosoft%2Ecom%2Fbuild-2025-book-of-news%2F&urlhash=2xHF&trk=article-ssr-frontend-pulse_little-text-block). A data scientist might have a machine learning model or complex data pipeline running on Databricks; now an AI agent can invoke that to answer a query. This means the insights data teams produce can be delivered on-demand to end-users through conversational agents. It also encourages collaboration: data teams can package their analytics as Genie queries or jobs, and AI developers can simply call them. Moreover, it “boosts productivity between business and technical users” by serving as a bridge[[3]](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Ftechcommunity%2Emicrosoft%2Ecom%2Fblog%2Fanalyticsonazure%2Fannouncing-the-availability-of-azure-databricks-connector-in-azure-ai-foundry%2F4414889&urlhash=PTYZ&trk=article-ssr-frontend-pulse_little-text-block) – data scientists can ensure the agent provides correct logic, and business users get the answers they need quickly. In short, data experts benefit because their work becomes more accessible and impactful via AI agents.
  • Business Users & Decision Makers: Perhaps the biggest winners are non-technical users like business analysts, managers, customer support reps – anyone who has questions that rely on data. Traditionally, such users either write reports, ask data teams, or use BI tools to get answers, which can be slow or require training. With AI Foundry agents connected to Databricks, business users can simply ask questions in natural language and get answers from their enterprise data[[2]](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Fwww%2Edatabricks%2Ecom%2Fblog%2Fannouncing-azure-databricks-native-connector-azure-ai-foundry&urlhash=x2z9&trk=article-ssr-frontend-pulse_little-text-block). Importantly, they can do this through familiar interfaces like Microsoft Teams as well (as demonstrated by Microsoft)[[3]](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Ftechcommunity%2Emicrosoft%2Ecom%2Fblog%2Fanalyticsonazure%2Fannouncing-the-availability-of-azure-databricks-connector-in-azure-ai-foundry%2F4414889&urlhash=PTYZ&trk=article-ssr-frontend-pulse_little-text-block). For example, a sales manager could ask in a Teams chat with the agent, “What were my region’s sales this month and how does it compare to last month?” and the agent will fetch the answer from Databricks. This democratizes data access — even those who “aren’t directly interacting with Azure Databricks” can still gain insights from it via the agent[[3]](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Ftechcommunity%2Emicrosoft%2Ecom%2Fblog%2Fanalyticsonazure%2Fannouncing-the-availability-of-azure-databricks-connector-in-azure-ai-foundry%2F4414889&urlhash=PTYZ&trk=article-ssr-frontend-pulse_little-text-block). It empowers decision-makers to get timely insights without always funneling requests through data departments. Essentially, any stakeholder who needs data-driven answers but isn’t comfortable with query languages or navigating databases stands to benefit.
  • IT and Data Governance Teams: While not “using” the feature day-to-day, IT administrators and data governance officers benefit because this solution maintains control. They can approve AI agent deployment knowing that security and compliance policies are enforced (thanks to Unity Catalog)[[1]](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Fnews%2Emicrosoft%2Ecom%2Fbuild-2025-book-of-news%2F&urlhash=2xHF&trk=article-ssr-frontend-pulse_little-text-block). The integration means they do not have to worry about a rogue AI querying data it shouldn’t or bypassing audit logs – all interactions are authenticated via Entra ID (Azure AD) and logged in Databricks[[2]](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Fwww%2Edatabricks%2Ecom%2Fblog%2Fannouncing-azure-databricks-native-connector-azure-ai-foundry&urlhash=x2z9&trk=article-ssr-frontend-pulse_little-text-block). So, IT can enable innovative AI scenarios for business users without losing oversight. This alignment of AI innovation with governance makes their job easier in ensuring data usage remains compliant.

In summary, the integration caters to a broad range of enterprise profiles: developers and IT pros get easier development and management, data scientists/engineers get their work infused into new AI interfaces, business users get direct access to insights through natural conversations, and IT governance can breathe easy with security in place. It essentially helps technical and non-technical roles collaborate via AI, each reaping rewards in efficiency and productivity[[3]](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Ftechcommunity%2Emicrosoft%2Ecom%2Fblog%2Fanalyticsonazure%2Fannouncing-the-availability-of-azure-databricks-connector-in-azure-ai-foundry%2F4414889&urlhash=PTYZ&trk=article-ssr-frontend-pulse_little-text-block).

Use Cases – Three (hypothetical) User Stories

To illustrate how this integration can be used, here are three hypothetical user stories in an enterprise setting:

User Story 1: Real-Time Sales Insights – Maria is a regional sales manager. She wants to quickly get insights on sales performance without learning complex BI tools. Her company’s data team has all sales data in Azure Databricks. Thanks to the new Foundry-Databricks integration, the company’s AI assistant (built with Azure AI Foundry) can answer Maria’s questions directly. Maria opens Microsoft Teams and asks the agent: “What were my region’s sales this week and which product category performed best?” The agent uses Databricks’ AI/BI Genie to run a live natural language query on the sales data[[2]](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Fwww%2Edatabricks%2Ecom%2Fblog%2Fannouncing-azure-databricks-native-connector-azure-ai-foundry&urlhash=x2z9&trk=article-ssr-frontend-pulse_little-text-block). Within seconds, it replies with a summary: “Your region sold £500k, up 5% from last week, with Product X being the top category.” It even offers to break down the numbers by product or generate a chart. Maria gets the answer immediately, in conversation form, without waiting for an analyst. This story shows how a business user can get real-time analytics through a simple question, leveraging Databricks data via the AI agent. It highlights the power of natural language access to data for faster decision-making.

User Story 2: Augmenting Customer Support with Data – Contoso Ltd. has a customer support chatbot on their website built using Azure AI Foundry. Before the integration, the bot could answer only basic FAQs. Now, Contoso connects it to Azure Databricks where detailed customer data and order history are stored. When a customer asks the chatbot: “Where is my order #12345 and has it shipped?”, the AI agent can retrieve that information live from Databricks. Behind the scenes, it runs a Spark job or query against the order database on Databricks (through the connector) to find the latest status[[1]](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Fnews%2Emicrosoft%2Ecom%2Fbuild-2025-book-of-news%2F&urlhash=2xHF&trk=article-ssr-frontend-pulse_little-text-block). It then responds: “Your order #12345 is currently in transit and is expected to be delivered by Friday.” In another scenario, a customer might ask, “I had an issue with my last purchase, what refund can I get?” The agent, through Databricks, accesses the customer’s past purchase records and the company’s refund policy data to give a personalised answer. This user story shows an AI-powered customer service agent that can handle complex, account-specific queries by fetching data in real time. It improves customer experience by providing accurate, up-to-date answers (which previously required a support rep to pull up several systems). The integration makes the chatbot truly data-driven and context-aware, rather than just a static Q&A bot.

User Story 3: Data Scientist’s Analytics as a Service – Lee is a data scientist at Fabrikam Corp. Lee has developed a sophisticated predictive maintenance model that runs as a Spark job on Azure Databricks. It analyses IoT sensor data and predicts equipment failures. Normally, only data scientists or engineers would run this job and then share results. With the new integration, Lee’s team wraps this model execution into an Azure AI Foundry agent. An operations manager can now ask the agent: “Which machines are at risk of failure in the next 7 days?” The agent triggers Lee’s Databricks Spark job via the connector[[1]](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Fnews%2Emicrosoft%2Ecom%2Fbuild-2025-book-of-news%2F&urlhash=2xHF&trk=article-ssr-frontend-pulse_little-text-block). The Spark job crunches the latest sensor data and returns a list of, say, three machines with high failure probability. The AI agent then translates that into a user-friendly response: “Machines A, B, and C have high risk of failure within a week. It’s recommended to service Machine A immediately.” This story demonstrates how the integration lets a non-technical user call complex analytics on-demand through a simple question. Lee’s advanced data pipeline is now accessible through an AI agent interface. The benefit is twofold: the data science work has greater impact, and the operations team gets timely insights without needing data science knowledge. It’s like providing analytics-as-a-service through an AI agent. The heavy lifting (Spark jobs, ML algorithms) runs on Databricks, but the interaction is in natural language via Foundry. This also underscores the multi-agent workflow potential – the Foundry agent can coordinate with Databricks (and even other agents) to fulfill a request[[1]](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Fnews%2Emicrosoft%2Ecom%2Fbuild-2025-book-of-news%2F&urlhash=2xHF&trk=article-ssr-frontend-pulse_little-text-block).

These three scenarios, while simplified, show the versatility of the Databricks-Foundry integration: from instant business dashboards, to smarter customer chatbots, to accessible advanced analytics. In all cases, users get faster, data-informed answers, and the complexity of data retrieval or computation is hidden behind a conversational AI agent. The key point is that the agent can act as an intermediary between people and the vast data/compute power in Databricks, enabling new intelligent workflows across the enterprise.

What This Change Is Not For

Like any technology, this integration has its scope and limits. It’s important to understand what it doesn’t do or what it shouldn’t be mistaken for, so that expectations remain realistic:

  • Not a Replacement for Data Warehouses or BI Tools: The Foundry-Databricks connector enables conversational access to data and running of jobs, but it isn’t meant to replace analytical dashboards, reports, or traditional BI for complex analysis. In other words, an AI agent using Databricks is great for Q&A-style interactions and quick insights, but it’s not going to produce full BI reports or visualisations in the way tools like Power BI do. For extensive data exploration, charting, or multi-dimensional analysis, dedicated BI tools are still very relevant. The agent is complementary – it can retrieve specific figures or summaries, but users may still use BI tools for deeper dives. One should not confuse chatting with an AI agent with the broader capabilities of a full analytics platform. It’s a new interface to your data, not a wholesale replacement of existing analytics workflows.
  • Only as Good as the Data and Jobs Provided: This integration itself doesn’t magically improve data quality or create new analytics that don’t already exist. It leverages the data and computations in Azure Databricks. So, if the underlying data is outdated or a Spark job is flawed, the agent’s answers will reflect that. It does not solve data quality, modeling errors, or completeness issues – those are still on the enterprise to manage. Think of it this way: the agent is a savvy messenger that can fetch information, but the information must be there and trustworthy. Additionally, while Azure AI Foundry provides responsible AI measures (like content filtering), it doesn’t guarantee correctness of answers – the agent could still misunderstand a query or be limited by what it knows. So, this tool is not for getting infallible answers to any question; it’s constrained by the data you have and how well your Genie queries or Spark jobs are set up.
  • Requires Azure Databricks (and Azure AI Foundry) – Not General Purpose for All Data: By design, this connector is specific to Azure Databricks. Organisations that don’t use Databricks, or whose data is in other systems (e.g., on-prem databases or non-Azure platforms), don’t benefit from this particular integration. It is not a generic data connector for any source (though Azure AI Foundry may support other connectors separately). So, one limitation is that you need to have your enterprise data in Azure Databricks (or be willing to put it there) to use this feature. It’s also tied to Azure AI Foundry — which is a new service itself. Companies not using the Azure stack or those with different AI orchestration tools won’t find direct use here. In short, it’s most relevant for those already in the Azure ecosystem. This shouldn’t be confused with, say, OpenAI plugins or other generic solutions that connect AI to various databases; it’s a specifically Azure-centric solution. The upside is tight integration and governance, but the downside is a narrower scope of applicability.
  • Not a Fully Automatic AI Magic Wand: Building an AI agent with enterprise data still requires effort and planning. The announcement makes it easier, but not completely automatic. Developers will still need to configure the connector, define what data the agent can access, possibly craft the NLQ prompts or Genie room settings, and ensure Spark jobs are written for the agent to call. In other words, this integration is not a “zero-work” solution where you turn it on and the AI just knows everything. It shouldn’t be mistaken for an AI that automatically understands your business – you must still build and train the agent, define its knowledge base, and ensure proper prompts. The feature simply removes a lot of heavy lifting in connecting to data. So, it doesn’t solve the need for good agent design and oversight. You shouldn’t expect a junior analyst to turn this on and instantly have a perfect AI assistant – it will still require your skilled developers and data engineers to set up and fine-tune.
  • Not a Fully Matured Solution (Yet): As of the Build 2025 announcement, the Databricks integration with Foundry is in preview. This means it’s still evolving and might have some limitations that will be addressed in the future. Users should be aware that preview features usually are not recommended for mission-critical use. Instead, organizations should experiment with it, understand its capabilities, and perhaps use it in parallel with traditional tools until it gains full maturity and trust – but until then, treat it as an exciting new tool that complements your existing analytics and AI processes.
  • Distinct from Other AI/Data Features: Given Microsoft’s broad AI announcements, it’s worth clarifying what this integration is not. It’s not the same as Microsoft 365 Copilot (which focuses on Office documents and user productivity scenarios), nor is it the same as Power BI’s new “chat with your data” feature (though conceptually similar in using NL queries). Azure AI Foundry’s Databricks integration is tailored for building custom enterprise agents, not just querying a single dataset or generating charts in a report. Also, it’s different from Azure Cognitive Search or Azure OpenAI on your data, which vectorize documents to let AI search them. Here, the agent is actually executing live queries and jobs on a data platform. So one should not confuse Azure AI Foundry + Databricks with a simple Q&A bot over documents – it’s a more robust, operational solution tied into enterprise data pipelines. Understanding this distinction helps set the right expectations: this change is about bringing operational analytics into AI agents, not about general document Q&A or general cloud AI services.

In summary, the Azure Databricks-AI Foundry integration is a powerful step forward, but it has defined use cases. It excels at injecting real-time, governed data into AI agent interactions. However, it’s not a cure-all for every data or AI challenge. It doesn’t eliminate the need for quality data management, nor does it work outside the Azure/Databricks context. Users should see it as an enabler for specific scenarios – especially where natural language Q&A on enterprise data is needed – and not mistake it for a broad AI strategy on its own. With the right understanding, organisations can avoid misusing the tool or expecting impossible outcomes, and instead apply it where it adds the most value.
